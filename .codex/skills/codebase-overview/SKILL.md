# Codebase Overview

梳理真实代码中的模块边界、入口、依赖和数据流，帮助后续规划建立在项目事实之上。不要套用其他项目的目录、类名、框架或调用链。

## When to Use

- 用户要求介绍项目架构、模块职责、调用关系或数据流。
- 用户准备进行跨模块 Feature，且需要先了解现有结构。
- 现有项目上下文文档可能过期，需要用代码核对。

简单的单文件文字、颜色或间距修改通常不需要使用本 Skill。

## Workflow

1. 读取适用的项目指令文件（`AGENTS.md`、`CLAUDE.md` 等）以及已有项目上下文文档。若文档不存在，记录缺失，不要自行编造规范。
2. 识别技术栈和运行入口。优先检查包管理文件、构建配置、应用入口、路由、内容/数据定义和测试脚本。
3. 按职责而不是按文件罗列模块。对每个模块确认职责、输入、输出、依赖和边界。
4. 用文件路径、导出符号、脚本命令或配置字段作为证据。无法从代码确认的内容标记为“待确认”。
5. 只保留主要调用链和关键数据流，不展开辅助函数、样式细节或完整文件清单。

## Output Contract

按以下顺序输出：

1. 总览：项目用途、技术栈和运行形态。
2. 模块拆分：每个模块说明目录、职责、关键对象、输入/输出和依赖。
3. Mermaid 全局图：标出主要入口、模块调用和核心数据结构流向。
4. 核心数据结构：说明跨模块共享的配置、领域对象、内容模型或视图模型。
5. 主要调用链：按实际代码写出关键函数、组件或脚本，覆盖主路径即可。
6. 风险与待确认项：只列出有证据的耦合、边界、构建、运行时或文档漂移风险。

## Writing Existing Context Documents

- 用户明确要求补充项目架构文档时，才写入文件。
- 如果写入 `.ai_docs/project_overview.md`，先将 AI 推断内容标为“待确认”，不要把推断直接写成强制规则。
- 不覆盖用户已有的上下文文档；先报告冲突，并等待用户决定。
- 文档内容以当前代码为准，完成后列出未验证的假设。

## Guardrails

- 不使用预设项目的入口、目录、类名或调用图。
- 不把“按目录拆分”误认为“按模块拆分”。一个模块可以跨多个目录，也可以只占一个文件。
- 不因追求解耦而虚构服务层、适配器层或数据层。
- 不把架构梳理变成功能实现或重构；发现问题只记录风险和建议方向。
