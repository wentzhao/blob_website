# Plan Implement Dual Review

按已确认的计划实现代码，并把实现缺陷与设计决策分开处理。实现 Agent 可以修复局部实现问题；涉及架构、范围或计划变更时，必须暂停交给用户决定。

## Required Inputs

- 已由用户确认的计划文件路径。
- 是否允许创建或切换分支，以及目标分支名称。
- 测试/验收方式；若计划未定义，则从项目脚本和测试规范中确定。

计划文件存在不等于计划已获批准。未收到明确确认时，不得开始实现。

## Step 0: Preflight

1. 读取项目指令文件、计划文件，以及适用的项目上下文和规则文档。
2. 检查当前分支、工作区状态和目标分支。报告未提交改动，不要替用户 stash、reset、checkout 或覆盖它们。
3. 若缺少计划要求的规范文件，报告缺失项并暂停；不要伪造项目规则。若文档标记为“待确认”或“草稿”，只能作为事实线索读取，不得按其中的约定执行，并将其列为待决策项。
4. 在任何分支创建、切换或代码修改前，确认用户已授权该动作。

## Step 1: Implement the Approved Plan

创建实现 Agent，并向它传递一个明确的上下文包：计划路径、用户批准状态、仓库根目录、允许修改的范围、分支授权、现有工作区状态和测试命令。

实现 Agent 必须：

- 完整阅读计划和适用的项目规则。
- 只实现计划范围内的内容，记录修改文件和验证结果。
- 发现计划与代码事实冲突、需要扩大范围或需要改变架构时，停止实现并上报，不自行改写设计。
- 不执行提交、推送、创建 PR 或合并等后续协作动作。

## Step 2: Self-review and Fix

让实现 Agent 对改动执行三项检查：

1. 计划符合性：实际行为、文件范围和验收标准是否匹配。
2. 项目规则：命名、模块边界、依赖和实现方式是否符合已确认规则。
3. 验证结果：执行受影响的测试、类型检查、构建或项目规定的手工检查。

发现局部实现错误可以直接修复并重新验证。若修复需要改变计划、公共接口、模块边界或用户可见行为，必须暂停并交给用户决定。

## Step 3: Independent Structural Review

创建只读的独立审查 Agent，审查范围仅限当前计划和当前改动。它必须基于代码证据检查：

- 模块职责和依赖方向；
- 不必要的耦合、重复或过度抽象；
- 静态生成/运行时、数据/视图等边界（适用于项目）；
- 计划外行为、公共接口风险和明显的可维护性问题；
- 与测试或验收标准不一致的结构性缺口。

每条问题包含：严重级别、文件和符号、证据、影响、建议方向。审查 Agent 不修改代码；没有问题时明确写“无结构性问题”。

## Step 4: Main Agent Report

主 Agent 只返回决策所需信息，但不得隐藏失败状态：

1. 分支和工作区状态；
2. 改动文件摘要；
3. 测试/构建/手工验证结果；
4. 计划偏离或需要用户决策的事项；
5. 独立结构审查问题。

若存在测试失败、计划偏离或设计决策，结论必须是“暂停，等待用户决定”。只有在验证通过且无待决策事项时，才能报告本轮实现和结构审查完成。

## Output Contract

```text
状态：<完成 / 暂停等待决策 / 验证失败>
分支与工作区：<状态>
改动摘要：<文件和目的>
验证结果：<命令或检查 + 结果>
计划偏离与待决策：<无 / 清单>
结构性问题：<无 / 清单>
后续动作：<等待用户 / 可进入提交或 PR 阶段>
```

## Guardrails

- 不把任何默认行为解释为用户已授权分支操作或代码修改。
- 不在脏工作区中自动清理、隐藏、回滚或覆盖已有改动。
- 不用实现 Agent 自己的结论替代独立结构审查。
- 不因测试暂时失败而宣称审查通过。
- 本 Skill 不负责提交、推送、创建 PR 或合并。
