# 项目级 Skill 使用指南

本目录包含当前项目可用的项目级 Skill。Skill 用来约束特定类型任务的工作流程；不需要每次都使用全部 Skill，应根据任务目标选择最匹配的一个。

## 如何调用

在提示词中直接写出 Skill 名称即可，也可以使用 `$` 前缀：

```text
请使用 $codebase-overview 梳理当前项目的架构。
```

如果任务涉及多个阶段，建议分阶段调用，而不是让一个 Skill 同时承担规划、编码、审查和发 PR 的所有工作。

## Skill 速查

### `codebase-overview`

适合：

- 介绍项目整体架构
- 说明模块职责、入口和依赖关系
- 解释调用链、数据流或核心数据结构
- 补充项目架构文档

它会先按模块拆分系统，再说明每个模块的职责、输入、输出和依赖，并输出 Mermaid 调用流程图。它更适合“阅读和解释项目”，不适合直接实现功能。

示例提示词：

```text
请使用 $codebase-overview 梳理当前项目架构，重点说明页面入口、核心模块、数据流和主要调用链，并输出 Mermaid 流程图。
```

注意：当前 Skill 中保留了 Paper Tracker 的模块示例。如果用于其他项目，应以实际代码为准，不要照搬示例中的目录或类名。

### `feat-plan-challenge`

适合：

- 已经明确一个较复杂的 Feature，但还没有实现计划
- 希望一个 Agent 先制定计划，另一个 Agent 独立挑战计划
- 需要识别设计冲突、遗漏场景和过度设计
- 希望只把需要用户拍板的事项带回主对话

它的流程是：生成计划 → 独立挑战 → 回传建议并合并 → 汇报冲突点和待决策项。

示例提示词：

```text
请使用 $feat-plan-challenge，为当前博客增加文章标签筛选功能。
先生成完整实现计划，再让独立 Agent 挑战审查，最后只告诉我冲突点和需要我拍板的事项，不要直接修改代码。
```

适用边界：简单的颜色、文字、间距或单文件修复通常不需要使用它。Feature 描述应包含目标、范围、约束和已知限制；缺少的信息如果不会改变方案，可以由 Agent 显式记录假设。

### `plan-implement-dual-review`

适合：

- 已经有明确的项目计划文件
- 希望按计划在新分支实现代码
- 希望实现 Agent 先按代码规范自审并修复
- 希望另一个 Agent 做结构性审查

它的流程是：读取计划并实现 → 按代码规范自审并修复 → 独立结构审查 → 汇报结构性问题。

示例提示词：

```text
请使用 $plan-implement-dual-review，按照 docs/plan.md 实现这个功能。
实现前阅读并遵守项目规范，完成后执行测试、自审和独立结构审查，最后只汇报结构性问题。
```

开始前应提供：

- 计划文件的路径
- 是否允许创建或切换新分支
- 需要执行的测试或验收方式

如果计划或项目缺少该 Skill 要求的规范文件，应先说明缺失项，并根据现有项目规范采用明确假设，不要伪造文件内容。

### `create-pr`

适合：

- 代码已经完成并通过必要验证
- 改动已经提交到非默认分支
- 需要根据提交记录生成并创建 GitHub Pull Request

示例提示词：

```text
请使用 $create-pr，为当前分支创建 GitHub Pull Request。
先检查当前分支、提交记录、远程状态和项目 PR 规范，再生成英文标题和描述；如果缺少提交或远程分支，先告诉我缺什么。
```

使用前检查：

- 当前分支不是 `main` 或 `master`
- 存在相对于目标分支的提交
- 远程仓库信息已确认
- 分支已经推送，或用户明确允许推送
- GitHub 认证和对应 MCP 能力可用

创建 PR 属于外部协作动作。生成标题和描述后，应先展示预览，在真正创建前确认内容和目标分支。

## 推荐工作流

复杂功能可以按照下面的顺序拆分：

```text
codebase-overview
        ↓
feat-plan-challenge
        ↓
plan-implement-dual-review
        ↓
create-pr
```

对应的组合提示词示例：

```text
先使用 $codebase-overview 了解当前博客的文章、导航和搜索架构。

然后使用 $feat-plan-challenge，为“增加标签筛选”生成并挑战实现计划，不要改代码。

计划确认后，再使用 $plan-implement-dual-review，按照计划实现、测试并完成结构审查。

代码验证通过并提交后，最后使用 $create-pr 创建 Pull Request。
```

## 选择原则

- 只想了解代码：使用 `codebase-overview`。
- 只有需求、没有计划：使用 `feat-plan-challenge`。
- 已经有计划、需要落地：使用 `plan-implement-dual-review`。
- 代码已提交、需要协作合并：使用 `create-pr`。
- 只改少量样式或文案：通常直接提出修改即可，不必启动多 Agent 流程。

## 常见问题

### Skill 没有被调用

在提示词中明确写出完整名称，例如 `$feat-plan-challenge`。同时说明希望 Skill 负责的阶段，例如“只制定计划，不修改代码”。

### 不知道该从哪个 Skill 开始

先使用 `codebase-overview` 了解项目；如果需求已经清楚但方案复杂，再使用 `feat-plan-challenge`。

### 可以一次调用所有 Skill 吗

不建议。Skill 有明确边界，按任务阶段调用更容易保留上下文，也能避免不必要的分支、审查和外部操作。
